# P1b + P2a — Clone node + Offsite backup (один заход)

Обе фичи — небольшие, раздельные, делаются параллельно в одном заходе (8 шагов). Каждая независимо компилируется и тестируется. Никакого e2e/VPS — чистая модель + хендлеры + UI; deploy-путь трогаем только переиспользованным `ApplyChain` (clone) / `UploadText` (backup), которые уже работают.

**Решения (подтверждены вами):**
- **P1b clone:** конфиг + копия ForUsers + копия ExitTargets; **identity всегда свежая** (UUID/Reality keys/ShortID/AWG client keys/MTProxy secret/transit WG keypairs/transit UUID/transit IP — всё регенерируется). Clone = "relocate, но с новой ID + свежей identity вместо переиспользованной, и новый ChainNode добавляется в цепочку (append), а не мутируется на месте".
- **P2a backup:** пароль хранится в `PanelSettings` (в уже зашифрованном at-rest сторе master-ключом) → включает и периодический цикл, и on-demand "Backup now". Master-key файл НИКОГДА не покидает хост (существующий `ExportStore` уже отдаёт plaintext, оффсайт-слой перешифровывает паролем). Восстановление: пароль вводится отдельно (он в scrypt-параметрах блоба, не в самом блобе).

# P1b — Clone node

## A1. Ядро — `internal/chain/clone.go` (НОВЫЙ, рядом с relocate.go)

Зеркалит `RelocateNode` (relocate.go:77) по структуре, но с двумя ключевыми отличиями: **новая ID** + **свежая identity**.

```go
type CloneReport struct {
    SourceID    string
    NewID       string
    NewAddr     string
    Chains      []CloneChainResult  // re-deploy outcome per affected chain
}
type CloneChainResult struct {
    Name    string
    Success bool
    Error   string
    Nodes   []NodeResult  // reuse model/chain NodeResult
}

// CloneNode duplicates a node's CONFIGURATION onto a new VPS with FRESH identity:
// new node ID, regenerated UUID/Reality keys/ShortID/AWG keys/MTProxy secret +
// fresh transit material per chain. ForUsers + ExitTargets are COPIED (the clone
// serves the same users + same exit topology shape). The source node is untouched.
// The clone is appended (new ChainNode) to every chain the source belongs to,
// then ApplyChain re-deploys those chains so dependent hops learn the clone's addr.
func (a *Applier) CloneNode(ctx, store *Store, sourceID, newID, newAddr, newUser, newKeyPath string) (*CloneReport, error)
```

Поток (переиспользует паттерн relocate.go:96-176):
1. `store.GetNodeInfo(sourceID)` + `store.GetChainsForNode(sourceID)` — исходный NodeInfo + список цепей.
2. **Коллизия-чек новой ID:** `store.GetHost(newID)` — если уже есть, вернуть ошибку (как capture nodes.go:179). Новый ID — из формы (operator-заданный), НЕ автогенеренный (соответствует существующему UX).
3. **Скопировать NodeInfo** в новый: `Country/Bandwidth/AutoApply/UseSudo/Source` (→ "cloned") + новый `Host{ID:newID, Addr:newAddr, User:newUser or source.User, KeyPath:newKeyPath or source.KeyPath}`. Очистить `LastDeployedHash/At` (не деплоено), `PendingHostKeyFingerprint`, `Takeover`.
4. **Свежая identity для каждого NodeInbound** (`stripAndRegenInboundIdentity`, см. A2): UUID, ServerPrivKey/PubKey, ShortID, Tag, ObfsPassword, TLSCert/Key, AWGClientPub/Priv — регенерировать; `Protocol/Port/Obfuscation/ForUsers/OutboundTag/Source/AWGServerAddress` — копировать (AWGServerAddress — config, но если совпадёт subnet с source → см. риск I.4; в этом слайсе копируем как есть, флаг).
5. `store.SaveHost(newHost)` + `store.SaveNodeInfo(newInfo)`.
6. Для каждой цепи source: **добавить новый ChainNode** (append в `chain.Nodes`) с **свежими transit-полями** (`regenChainNodeIdentity`, A2): TransitPrivKey/ShortID/UUID, TransitAWGServer*/Client*/Address, ExitAWG*/ExitAWGLinks — всё регенерировать; `Port/Role/ExitTargets/Inbounds` — копировать из source ChainNode; Host-поля → новые (newID/newAddr/newUser/newKeyPath). `store.SaveChain(c)`.
7. **Re-deploy** каждой затронутой цепи через `a.ApplyChain(ctx, store, c, "")` (тот же интерфейс, что relocate.go:146-170). ApplyChain увидит свежие transit-ключи как непустые → переиспользует их (не генерирует заново).
8. `chain.WriteAudit(store, "clone", "node", newID, AuditPayload{"source": sourceID, "new_addr": newAddr, "chains": chainNames, "success": count}, "operator")`.
9. Вернуть `CloneReport`.

# Риски (помечены)

1. **AWGServerAddress коллизия** — копируем subnet source-клона как есть (по решению "копировать config"). Если source AWG inbound = `10.8.0.1/24`, clone = тоже `10.8.0.1/24` — но это **на разных нодах** (разные VPS), так что локальный конфликт невозможен; конфликт только если обе ноды в одной цепочке и роутинг пересекается. Флаг в CloneForm: "AWG subnet copied as-is — change if the clone joins the same chain". P1b+ : автолюбка свежего /24.
2. **ExitTargets — это ID** — копируем как топологию (по решению). Клон exit-ноды будет таргетить те же exit-ID, что source. Если source был exit с ExitTargets=["exit1"], клон тоже таргетит exit1 — это валидно (балансер на 2 exit). Если source был entry с ExitTargets, клон наследует — тоже валидно.
3. **Backup passphrase в сторе** — в at-rest-зашифрованном (master-key) сторе. Без master-key файла стор plaintext → пароль виден. Документировано: "enable master-key encryption (store.json.key) for at-rest protection of the passphrase". Это операторский выбор, не блокер.
4. **Clone re-deploy гонит ApplyChain по реальным VPS** — в тестах мокаем applier (chainApplier интерфейс), не диалим. В проде ApplyChain деплоит — но это существующая, работающая функция (relocate её использует). Без e2e-проверки клона в этом слайсе (как и relocate не имеет e2e — только unit).
5. **Backup SSH target ≠ managed node** — `UploadText` идёт через тот же SSH-connector, но к произвольному хосту (offsite-бокс), не к ноде. TOFU host-key проверка: offsite-target — это новая запись в known_hosts; первый коннект потребует доверия. В MVP — переиспользуем существующий connector (TOFU как для нод), флаг: "first offsite connect may prompt host-key trust".
6. **scrypt N=2^16 ~64MB** — память на каждый backup. На слабом оркестраторе это тяжело; но backup раз в 6ч — приемлемо. Флаг; P2a+ : тюнимый N в cfg.

# Явные не-цели

P1b: без e2e-проверки клона на реальном VPS (мок applier, как relocate). Без авто-генерации newID (operator-заданный, как capture). Без автолюбки свежего AWG subnet (копируем, флаг).
P2a: без restore-from-remote-pull (operator скачивает блоб вручную → paste в restore). Без retention/rotation на offside-target (один блоб per backup; перезаписывается по remote_path — operator управляет retention). Без master-key бэкапа (master-key НИКОГДА не покидает хост — это принцип). Без e2e SSH-пуша (мок-connector в тестах).
